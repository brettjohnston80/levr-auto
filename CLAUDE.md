## Working Preferences (read this before doing anything)

- **Plan before code, always.** Propose schema, UI surfaces, and open design questions before writing any implementation code on non-trivial changes. No surprises.
- **Verify against source files — never take documentation at face value.** Validate claims against actual implementation files, not memory or prior docs. Flag inconsistencies explicitly rather than silently resolving them — several real bugs this project has caught (an RLS policy mismatch, a stale full_name reference, a scoring function that didn't use most of its inputs) were found exactly this way.
- **Real-data verification gate.** No feature is done until verified end-to-end with real data, not just "the code compiles." Test artifacts get cleaned up after, confirmed via grep.
- **Migration workflow: Claude reviews, Brett runs.** Migrations are always reviewed by Claude, then run manually by Brett in the Supabase SQL Editor — never auto-run, even when confident it's correct.
- **Customer-facing copy needs explicit sign-off** before being built or logged as approved.
- **Secrets never in chat.** `.env.local` only — no Stripe/Supabase secret values ever pasted into a Claude Code session or a chat.
- **Claude Code boundaries:** may self-execute CRON_SECRET-gated commands against Brett's locally-running dev server; must not start the dev server unprompted; must not delete or modify files a live Turbopack process depends on without flagging first.
- **Output format:** plain numbered lists for step-by-step instructions, not step-card widgets. All SQL, terminal commands, and Claude Code handoff instructions delivered as plain, directly copy-pasteable code blocks in chat — never as downloadable files.
- **Long terminal output:** write to a file and drag it from Finder into chat — line-wrapping corrupts long pastes otherwise.
- **Session continuity:** the "Start Here" section below is designed to be copy-pasted as the opening message of every new Claude.ai chat session.

## What this business does

LEVR Auto negotiates new-car purchases on behalf of consumer buyers, nationwide. Customer picks one make/model, pays a flat $699 fee, LEVR sources matching dealer inventory and negotiates by phone/email, offers land in a dashboard, customer accepts one. Money-back guarantee if no below-MSRP offer within 30 days.

Legal entity: **LEVR Holdings LLC** (Kansas). Public brand: **LEVR Auto**.

Full business logic lives in `LEVR-Auto-Core-Processes-v1.md` and `LEVR-Auto-Business-Plan-and-Roadmap.md` in this repo — read those for anything not covered here.

## Approach & patterns

- **Self-execution boundary for test/verification commands (decided 2026-08-15).** Claude Code may self-execute test/verification commands directly against Brett's live local dev server, but only when both of the following hold:
  - **The dev server is already running.** If it isn't, don't start it unprompted — ask first. Starting it is a state change outside what was requested, even though it's low-risk.
  - **Only non-secret-shaped credentials are used to authenticate** (e.g. `CRON_SECRET`, whose local-testing value doesn't pattern-match a real secret and so isn't redacted from tool output). Never attempt to read or use actual Stripe/Supabase secret values directly, even if they somehow became readable — those stay exclusively something Brett runs himself, same as every migration this project has ever used.
  - **Why this is safe:** Claude Code's Bash tool runs directly on Brett's own machine, in this project directory — there's no sandbox boundary between it and whatever Brett has running in another terminal. Hitting `localhost` from Bash is functionally identical to Brett typing the same curl command himself. What actually gates this is credential *readability*, not network access: `.env.local` reads come back redacted for values that pattern-match known secret formats (Stripe's `sk_`/`whsec_` prefixes, Supabase's JWT-shaped service-role key), so those can't be used even when the dev server is live and reachable. `CRON_SECRET` isn't redacted, which is what makes scratch/test-route verification (e.g. the extension-payment-flow pass, 2026-08-15) self-executable without Brett needing to run the curl commands himself.
  - **Scope: this covers scratch/test-route verification against local dev only.** It changes nothing about migrations, production data, or real payment/webhook actions against Stripe/Supabase directly — those still always go through Brett's own hands, exactly as before.
  - **Narrowed after a real incident (2026-08-15): this permission covers HTTP requests to the running dev server only — it does not extend to deleting or modifying files the live process depends on** (e.g. `.next`). A running Turbopack instance expects to own that directory continuously; deleting it mid-session (done here to clear a stale TypeScript error) wedged the live server into a state where it stopped responding to any request at all, including plain `GET /`, requiring Brett to restart it by hand. `.next` deletion in isolation is normally safe/disposable — the mistake was doing it without accounting for a live process already depending on it. **Standard going forward: any action that could disrupt the live server itself, not just query it, needs to be flagged before doing, not after** — the same bar test/verification HTTP requests are already held to, just missed once here.

- **Cross-channel messaging consistency (decided 2026-08-15).** Customer-facing copy must stay consistent in substance across every channel/format it appears in — email, dashboard banners, in-app confirmations — same core facts and tone, even when the exact wording adapts to fit the format (e.g. a banner uses a live countdown, an email uses a fixed date). Applies to all future customer-facing copy, not just Day-60 — when writing or reviewing copy for a flow that already has approved copy in another channel, check that channel first rather than drafting independently.

- **Key learnings & principles — `customers.email` is non-unique, denormalized display data (confirmed 2026-08-16).** Unlike `agents.email` (`text not null unique`, `initial_schema.sql`) or `auth.users.email` (uniqueness enforced separately by Supabase Auth itself), `customers.email` is just `text not null` — no constraint — and its own column comment already says it's a denormalized copy of intake/auth data kept for convenient reads (e.g. an agent-facing admin view) without joining into `auth.users`. Confirmed by reading the schema directly, not inferred. **Safe to write freely for test purposes** (e.g. a scratch route redirecting a test row's `customers.email` to a real inbox to verify a reminder email actually gets delivered) — **but never usable as a lookup key, in test or production code**, since two rows can legitimately (or accidentally, as in a test override) carry the same value. Confirmed via a full grep audit across `src/` that no production path does this today — the only `customers` lookup keyed by email anywhere was a scratch route's own cleanup logic, which broke exactly this way: a `setup` mode overrode a test row's `customers.email` to a real address for delivery testing, and the matching `cleanup` mode's by-email lookup then silently found nothing, leaving the row orphaned until a by-id fallback was added. **Lesson for future scratch routes:** if `setup` overrides a denormalized field like this, `cleanup` must key off the row's real `id`, never off the field that was overridden.

- **Key learnings & principles — a single status transition's guard logic can be duplicated across four independent layers, and extending one doesn't confirm the others were caught (confirmed 2026-08-21).** Gating "can this search move from status A to status B" showed up in this codebase as: a DB check constraint (which statuses are even legal), an RPC's own guard (which of those the specific transition allows), a client-side render condition (whether a button/control shows at all), and — found the hard way this pass — a separate, independently-hardcoded allow-list inside the Server Action itself, checked as a pre-flight gate before the RPC is ever reached. Extending `cancel_search`'s purchased-status support meant updating the RPC guard and `canCancel()` in `account/page.tsx`, both of which looked complete and both of which compiled/rendered fine — but `cancellation-actions.ts`'s own `CANCELLABLE_STATUSES` constant was a fourth, silent copy of the same list, missed by both the migration and the `canCancel()` review, and it alone was enough to keep the real customer flow broken. **The lesson: when a plan says "extend this status guard," grep every reference to the concept (`grep`-ing for the actual status strings involved, e.g. `'searching'`, `'purchased'`, together — not just the function/file names a plan happens to mention) before calling the change complete, and verify through the real end-to-end flow (real UI, real Server Action), not just a direct RPC call — a direct RPC call would have passed cleanly here and hidden this exact bug.**

## Critical schema decisions already made — implement these correctly from the start

**`listings` vs `qualifying_offers` — these must be separate tables, not one.**
- `listings` = raw MarketCheck data (VIN, dealer, price, MSRP, trim, synced_at). Just sourced inventory, refreshed on a cadence.
- `qualifying_offers` = ONLY populated when a dealer actually responds to outreach with a real, itemized offer they're willing to honor. **An advertised listing price is never automatically a Qualifying Offer** — this is a hard business rule, not a UI nuance. Only rows in this table count toward the 30-day guarantee.

**`customer_searches` table doubles as the demand registry.** Drives MarketCheck sync cadence:
- Any make/model with an active row here → sync nightly
- Everything else → weekly, or monthly for consistently low-movement makes/models
- Rationale: most of the national inventory has zero active customers on any given day; pulling all of it nightly wastes API budget for no product benefit

**`assigned_agent_id` on every customer case, from day one** — even though right now it only ever points to Brett. This is what guarantees continuity (same agent stays with a customer) once there's ever a second person on the team. Cheap to build in now, annoying to retrofit later.

**VIN is the de-duplication key** for `listings` — upsert on VIN, never insert-always, or re-syncs create duplicate rows.

**Every MarketCheck sync call needs an explicit `car_type=new` filter** — testing showed the API defaults to mostly used inventory without it.

## The guarantee — exact rule (already decided, implement precisely)

- MSRP = Monroney label total (base + factory options + destination), excludes tax/title/doc/dealer add-ons
- Qualifying Offer = any dealer offer below that MSRP on a matching vehicle
- Assessed at Day 30 from solidification — not payment. The customer has a 24h post-payment refinement window to fine-tune trim/color/options; the clock starts once that's locked in (`solidified_at`), not at the moment of payment (`paid_at`). Changed 2026-08-12 — see the Day-30/solidify entries below.
- **Sold-to-someone-else edge case:** customer gets a 24-hour response window from when a Qualifying Offer is delivered. No response within 24hrs + car sells → offer still counts (guarantee satisfied). Customer responds within 24hrs but car sells before it goes through anyway → doesn't count, LEVR keeps searching.
- Free search continues through Day 60 either way. After Day 60: $100 per ~30-day extension.
